Design board

Account signup

A responsive signup surface for survivingthesingularity.com. Drawn mobile first, resolved at desktop, then checked back through tablet. Every preview below is the same single file rendered live at a different width, not a mockup image.

Live previews Mobile first 3 breakpoints Container queries 280px to 4K
01 / Wireframes

Structure before surface

The order the layout was reasoned in: phone first, because that is the hardest constraint and the majority of traffic. Then desktop, because that is where the extra width has to earn its keep. Tablet last, as the resolution between them.

1. Mobile 390 × 844 · base layout

The one decision that matters here: the card comes first and the value rail second. Someone arriving on a phone from a checkout link already decided. Making them scroll past four benefit bullets to reach an email field is a tax on a user who is already converted. The rail is still there, underneath, for the ones who need convincing.

2. Desktop 1440 × 900 · two pane

Width has to be spent, not just filled. The card is pinned to a 420 to 480px column and the rail takes the remainder. A form that stretches to 700px is worse than one that does not: the eye has to travel the full width of an input to find a 40 character email. The extra desktop space goes to the argument, not the fields.

3. Tablet 834 × 1112 · centered narrative column, and why it is not a split

Tablet is where most responsive designs go wrong, because 768px is the reflex breakpoint and it is the wrong one for a two-pane layout. Split an 834px tablet and each pane gets roughly 380px: the rail copy sets at about 30 characters per line, which reads as a ragged column, and the card drops back to stacked federated buttons anyway. So the split waits until 1140px. Between 900 and 1139 the page composes as one centered narrative column instead, which is a better use of that width than a bad split.

02 / Thresholds

Three breakpoints, and each one has a reason

A breakpoint is a claim that something breaks. Each of these was placed by widening the window until the layout actually failed, then setting the threshold just before the failure. Everything between them is fluid, so the layout is continuous rather than stepped.

ThresholdWhat changesWhy there and not elsewhere
base
< 560px		 Single column, card first. Rail below. Federated buttons stacked. Wordmark reduced to the glyph. The floor is 280px, which covers a folded Galaxy Z and a narrow browser side panel. Below 320 the card padding tightens via container query rather than a media query.
560px Benefits go 2-up. Full wordmark appears in the masthead. The benefit body copy hits a comfortable measure around 270px per column. Below that a 2-up grid produces four-word lines. This is also where a 500px square viewport crosses into readable.
900px Rail moves above the card and centers. One narrative column: argument, then form. Enough width for the rail to hold a 60 character measure at full width, but not enough for two panes. Tablet portrait (834px) sits just below this and stays in the mobile composition, which is correct: it is a phone layout with more room.
1140px Two panes. Rail left at 1.05fr, card right pinned to 420-480px. Benefits return to 1-up. The first width where the card can hold 480px and the rail still clears 500px. Tablet landscape (1112px) deliberately stays single column, since a 1112px split leaves the rail at 480px and the copy gets tight.
1600px Growth stops. Container caps at 1480px, gap opens to 120px, headline steps up. Past this the layout stops getting bigger and starts getting more air. Nothing on an ultrawide should be 1600px of input field.
height
≤ 760px		 Vertical rhythm compresses. Stack, card padding and headline all shrink against vh. Width is only half of responsive. An 800 by 600 window, a square viewport and a laptop with a browser toolbar all fail the same way: the submit button falls below the fold.
height
≤ 560px		 Rail collapses to its headline. Benefits, proof line and footer hide. Landscape phone. At 390 by 560 the rail is not persuasion, it is an obstacle between the user and the field they came for.
03 / Live

The same file at seven widths

Each frame below is signup.html in a real iframe at the labelled size, scaled to fit. Nothing here is an image, so what you see is what the CSS actually does. Scroll the strip sideways.

Note the two that usually get skipped: 280 × 653 (folded phone) and 500 × 500 (square). The square viewport is the real test, because it fails on height rather than width and most layouts only defend one axis.

04 / States

A form is not one screen

Every state below is reachable from the demo bar at the bottom of the live design.

DefaultEmpty, consent unchecked, submit enabled. No pre-emptive red.
FocusAmber border plus a 3px ring. Field background darkens so the active row reads first.
ErrorFires on submit, not on keystroke. Clears the moment the user starts fixing it.
StrengthFour segments, appears only once typing starts, in signup mode only.
LoadingButton becomes the spinner and states what it is doing. No layout shift.
Check emailCard swaps in place. Shows the address back, offers resend and correct.
Sign inSame card. Consent row and strength meter drop out, hint becomes "Forgot?".
Reduced motionOrbs stop drifting, spinner stills, transitions collapse to a single frame.
05 / Spec

What a build needs to know

Tokens are lifted from src/routes/+page.svelte so this surface matches the current homepage, not the older brutalist theme.

Palette

Amber carries the single primary action. Blue and green are reserved for state, never for chrome.

Type

  • Outfit for everything readable
  • JetBrains Mono for labels, eyebrows, strength meter
  • Headline clamp(1.65rem, 4.4vw, 3rem)
  • Inputs floored at 16px, which is what stops iOS Safari zooming on focus

Fluid primitives

  • --gutter: clamp(16px, 5vw, 56px)
  • --stack: clamp(14px, 2.6vw, 22px)
  • --card-pad: clamp(20px, 5.2vw, 40px)
  • --tap: 48px floor on every control

Container queries

The card is its own query context, so its internals key off the pane width rather than the viewport. Federated buttons pair at a card width of 380px and padding tightens under 320px. That means the card is correct if it is ever reused in a modal or a narrower shell.

Accessibility

  • Every control clears 48px, above the 44px WCAG 2.5.5 target
  • Errors are role="alert", strength is aria-live="polite"
  • Visible :focus-visible ring on everything focusable
  • Reveal toggle is a real aria-pressed button
  • forced-colors block restores borders in high contrast
  • Body text meets 4.5:1; muted metadata is decorative and duplicated in accessible copy

Open questions for build

  • Confirm which OAuth providers are actually enabled in Supabase before shipping both buttons
  • Magic link and password are both drawn. Pick one as primary, or ship both as designed
  • The site has no /login or /auth route today, so routing is a build decision, not a design one
  • Consent checkbox wording needs a legal read against the existing policies page
