The second book is cheap. The second novel isn't.

A 5,355-line tool carried Surviving the Singularity to 92,778 words, 2,076 addressable blocks, 1,330 traced claims and four output formats. Not one line of it writes prose. Here is what actually ports to the next book, measured command by command.

5,355lines in sts.py, stdlib only 22commands, zero that write prose 2,076individually addressable blocks 1,330claims with a chain of custody 65%of the tool ports to any book 64%of the claim surface dies in fiction

The short version

The system is not a writing system. It is an accountability harness, and its value on the next book scales with how many falsifiable claims that book makes. Roughly two thirds of the tooling ports to any long document unchanged. The remaining third is verification machinery that only earns its keep when the text asserts things about the world.

So: a second work of argued nonfiction reuses almost everything. A novel reuses the plumbing and loses the point. And in both cases the expensive part, the 92,778 words, is untouched.

Four numbers, all correct

Ask this project how long the book is and you get four answers, depending on which instrument you use.

The block index counts words inside parsed blocks. The section walker counts what book.json declares to be sections. The claim scanner reads the section files whole, so it picks up markup the parser drops. And wc -w on src/lib/data/book/*.md returns 100,887 because three markdown files live in the book directory and are not the book: the README, the voice guide, and a narrative protocol document.

That last one is the interesting failure. Thirty-three .md files sit in the source directory. Thirty of them are the book. The difference is not enforced by the filesystem, by a naming convention, or by anyone's memory. It is enforced by one file.

The gate: a markdown file in the book directory is not in the book until book.json lists it. There are ten files named book.json across this machine's repositories. Exactly one of them is canonical. The system's job is not to prevent the other nine. It is to make the question "which one is real" have an answer.

What the rig actually is

Twenty-two commands, one Python file, standard library only, no dependencies. It finds its own repository root and refuses to run if it cannot.

def repo_root() -> Path:
    here = Path(__file__).resolve()
    for parent in here.parents:
        if (parent / "svelte.config.js").exists():
            return parent
    sys.exit("sts.py: could not locate repo root (no svelte.config.js above me)")

Read that again, because it is the first portability constraint and it is four lines long. The book tooling locates itself by looking for a SvelteKit config file. The manuscript machinery is anchored to the website's build system. Nothing about counting words in a chapter requires SvelteKit. It requires it anyway, because that is what was in the room when the function was written.

Here is the more surprising number. Search the whole 5,355-line file for the book's own title and you find four occurrences. One in the help text, one in a version banner, two in generated credits. The tool barely knows what book it is operating on.

The part that is genuinely novel

Most manuscript tooling stops at "count the words". This one assigns every paragraph, heading, list and block quote a stable identifier, held in a sidecar index next to the prose rather than inside it.

id_scheme: sts.<section_id>.b<NNNN>   # b = block, 4-digit monotonic ordinal
totals:   {'sections': 30, 'blocks': 2076, 'words': 92778}

{"id": "sts.part-1.b0001", "type": "heading", "lines": [1, 1],
 "words": 6, "hash": "d1b073b7bce8", "preview": "# Part I: What is the Singularity?"}

Each entry carries a line span and a content hash. That combination is what makes a book programmatically editable without a word processor: an agent can fetch block sts.chapter7.b0042, rewrite it, and put it back, and the hash tells you whether anyone else moved it in the meantime. The markdown source stays clean, so building the index is not a content change.

The word "tombstones" appears in the index schema, one field per section. Blocks that were deleted leave a marker. The index remembers that something used to be there.

Why this matters for book two: this is the single most transferable thing in the repository, and it has no idea what the book is about. It parses markdown and emits ordinals. It would work on a cookbook.

Note what that output refuses to do. It does not report a score. It reports 679 claims as UNCHECKED and puts that number first, above the 455 it can support. It distinguishes a citation that returned a 200 from a citation whose cited title actually appears on the page. It separates a server that blocked the checker from a source that is dead, on the grounds that a refusal is not a failure of the citation.

And it tracks git receipts: for each claim, whether the file carrying it exists at origin exactly as committed, exists only locally, or is sitting uncommitted in the working tree. One file was uncommitted when I ran it. That is the harness telling on the author.

A book that says "trust me" and a book that says "679 of my claims are unchecked" are not the same object, and the second one is more trustworthy.

Alongside it, verify recomputes every calculation the book shows a reader, checks the subtitle and the price for drift between the site and the built files, and audits the internal precedent ledger. That last check contains the sharpest line of commentary in the codebase:

# How many Precedents the Ledger is supposed to contain. Asserted here on
# purpose rather than counted from Appendix D: the whole point of the check
# is to compare the chapters against an independent number, and deriving it
# from the index would make the comparison a tautology.
LEDGER_SIZE = 23

A hand-asserted constant, with a paragraph defending why it is not derived. This is a checker that was built by someone who understood that a check computed from the thing it checks is not a check. It is also, precisely because of that, the least portable line in the file.

The genre cliff

Here is where the answer stops being "fork it and swap the markdown".

The verification third of the rig, the expensive third, the part that took the most thought, only functions on text that asserts things about the world. Break the 1,330 traced claims down by type and you can see exactly how much of that machinery a novel would inherit.

A novel cites nobody, dates nothing against the record, links to no sources and quotes no statistics. That is 847 of 1,330 claims, 64 percent of the traced surface, with nothing on the other end of the trace. What survives is internal cross-references, which become continuity checks and are genuinely valuable, and image claims, which become figure bookkeeping.

Causal claims are the interesting middle. A novel makes them constantly and none of them are checkable against the world, because the world in question does not exist. You would want a different harness there: not "is this true" but "is this consistent with what chapter four established". Same shape, entirely different backend.

The honest limit of this whole evaluation: no second book has been built on this system. Not one. I checked every book-shaped project on the machine and found none of them running this pipeline. Everything below the line "what ports" is a forecast derived from reading the code, not an observation of it happening. A forecast from a careful reading is worth something. It is not worth what a second book would be worth.

The part that cannot be copied at all

The voice guide is 70-plus lines of specific instruction about how this book sounds. Three registers with named borders: the Argument, the Narrative, the Field Manual. Each rule followed by a real line lifted from the shipped prose so you can hear the target rather than infer it.

It opens by explaining what it replaced:

"This replaced WRITING_CHECKLIST.md, which was blog-era guidance (emoji headers, a 30% humor quota, 'Buckle up, buttercup' transitions) predating the v0.6.x techno-optimist turn and the v0.7.1 wake-up-call turn. Following the old checklist literally produced the wrong book."

That sentence is the most important thing in the repository, and it is a warning aimed directly at anyone planning to fork this for a second book. The old guide was not vague or badly written. It was specific, actionable, and wrong, and being specific is exactly what made it dangerous. An agent following it produced prose that was confidently off-target.

The current guide is right because it was written against shipped prose rather than against intent. Which creates the bootstrapping problem: you cannot write book two's voice guide until book two has a voice, and the voice emerges from writing. There is no shortcut. Inheriting the StS guide would hand book two the wrong three registers with total confidence.

Every generic thing in this system ports for free. Every specific thing has to be re-earned. And the specific things are the ones that made the book good.

Does your command port? A decision procedure

If you are forking this, run each command through three questions in order. The answer to the first one that fires is the answer.

The answer

Split it by what you are actually asking.

Another argued nonfiction book, same author, same site

The plumbing is close to free. Fork the repository, replace 30 markdown files and the seven top-level keys of book.json, delete or replace LEDGER_SIZE and its ledger checks, point Stripe at a new product, and 3,345 lines of manuscript tooling start working immediately on prose they have never seen. The block index rebuilds itself. Then you write 90,000 words, which is the entire cost and always was.

A novel

Same plumbing, and about a third of the rig becomes dead weight you are maintaining for nothing. scan, id, compile, refs, flow, backup, quotes are all still excellent. verify math has no calculations to recompute. factcheck loses 64 percent of its claim surface. You would be better served building the fiction equivalent, a continuity harness over the same block index, than porting the fact harness and watching it report zero.

A different author

Everything above, plus the voice guide has to be re-derived from scratch, and it cannot be derived until there is prose to derive it from. Budget for writing a substantial chunk of book two badly, then writing the guide against what that chunk revealed, then rewriting the chunk. The StS guide names that exact sequence as the thing that went right.

What to take from this

The instinct when a project goes well is to package the tooling and reuse it. That instinct is correct and it under-describes what happened here. The 5,355 lines are not the achievement. They are the residue of noticing, 611 commits deep, which things had gone wrong often enough to be worth mechanizing.

What generalizes is not the file. It is three habits the file encodes, and you can adopt all three tomorrow on a project that has no Python in it at all.

Name the canonical copy and make everything else generated. Ten book.json files exist. The system does not prevent that. It makes exactly one of them load-bearing and treats the rest as output, so the question "which is real" has an answer instead of an argument.

Give the long document addresses. 2,076 stable block ids with content hashes are what turn a manuscript from a thing you open into a thing you can operate on. This is the highest-leverage and least-copied idea in the repository.

Report the unchecked count first. 679 UNCHECKED above 455 SUPPORTED. A harness that leads with its own coverage gap is one you can trust the rest of. A harness that leads with a green score is a harness nobody has ever watched fail.

And the finding that started this: not one of the 22 commands writes a sentence. The system's entire contribution to a 92,778-word book was making it impossible to lose track of what the book said. That contribution is large, it is real, and it scales precisely with how much the book is willing to be checked.

What I did not verify

No second book has been built on this system, so the portability verdicts are readings of code rather than observations of a port. I did not attempt a fork. I did not run any command against a different manuscript. The line-count classification is measured; the three-way verdict on each command is my judgment from reading the function, and a real port would move some commands between columns. The fiction claim-survival split is my classification applied to real counts, not something the harness computes. The EPUB and PDF file sizes are directory listings, not verified builds.
