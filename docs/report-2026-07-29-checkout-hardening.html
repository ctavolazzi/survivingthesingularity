02 / WHAT I FIXED, PART ONE

Four API routes were waving through exactly what they existed to stop

Every state-changing endpoint carried its own copy of the same three lines. The check was meant to reject cross-site POSTs. Because of one &&, it rejected honest browsers on other sites and let scripted clients walk straight through by simply not sending a header.

Why it stayed broken for a day

This exact bug was found and fixed in /api/waitlist on 2026-07-28, verified live, and written up. The other four routes carried their own copies of the same three lines and nobody went looking for them. One fix, five files, four of them missed.

The copies were the bug. The check now lives in one module, $lib/server/sameOrigin.js, and every route calls it. The next fix cannot miss four files because there is only one file to fix.

Which route mattered most

/api/stripe-checkout. Unguarded, a script could create checkout sessions at will: junk in the transaction ledger, junk in Stripe, and a rate-limited endpoint on the money path standing wide open.

The other four were smaller but real: /api/checklist-email and /api/waitlist each fire a Resend email per request. The cost of a flood is not database rows. It is your sender reputation, which is much harder to repair.

Checked before changing, rather than assumed

Failing closed breaks any legitimate client that does not send an Origin header, so I looked for one instead of hoping. Every caller of all five routes is a same-origin fetch() from this site, and nothing in the codebase emits a List-Unsubscribe: One-Click header, which is the one realistic case where a mail provider POSTs to you with no Origin. A same-origin Referer is still accepted as a fallback for privacy tools that strip one header but not the other.

A 403 on every request would also be "all fixed" by a careless reading, and it would mean the site is broken. The positive controls prove real traffic still works. One trap worth writing down: do not run this probe with Content-Type: text/plain. SvelteKit's built-in CSRF guard rejects that content type first, and both the broken and the fixed case return 403, which makes the test look like it passed no matter what.

The tombstone

claimSession() inserted the "this session is handled" row before minting the download, writing the preorder and sending the email. Any crash in between left a row that said done and meant began. Stripe would retry, the claim came back already taken, the webhook answered 200, and a paying customer got nothing.

The fix

The row now records an outcome, so three cases are distinguishable where there was one: delivered means stand down, claimed and fresh means another worker is mid-flight, claimed and older than two minutes means the first attempt died and this one repairs it.

The ledger

checkout_transactions is one row per session, never purged, carrying amount, currency, payment intent and status. fulfilled is a separate column on purpose. "They paid" and "they received it" are different questions, and conflating them is how the hole above stayed invisible.

05 / WHAT I FIXED, PART TWO

The backup was written twice and scheduled zero times

Requirement six asked for data in more than one place behind a single operational gate. What existed instead was two competing backup scripts writing into the same folder, neither of them automated. That is the opposite of a single gate.

Why sts.py won

It discovers tables from the PostgREST OpenAPI document instead of carrying a hardcoded list. That is not a style preference. The .mjs list was written before checkout_transactions and email_deliveries existed, and it already missed preorder_counts.

A migration nobody tells the script about is silently absent from every backup after it. That is precisely the failure that makes people trust a backup which does not contain their data. On tonight's run, discovery picked up all seven objects.

Verify, do not assume

Each table is now cross-checked against the server's own exact count, and a short read is an error that fails the whole run. A truncated dump looks identical to a complete one, and the gap only surfaces during a restore, which is the worst possible moment to find it.

Tonight: 7 of 7 tables verified, 34 rows, exit status 0 under launchd rather than only by hand.

Two deliberate limits, stated rather than hidden

Nightly runs skip the storage files. A full backup also pulls the 94 MB research bundle. That file is immutable, so storing it 365 times a year would spend 34 GB on one file, and this disk is at 93 percent. The bucket inventory is still recorded nightly, so a bundle that changed would show up in the diff, and one complete copy including the file exists at 2026-07-28-2.

The schema snapshot captures columns only. Not indexes, constraints, defaults, foreign keys, RLS policies, triggers or functions. It is a reconstruction aid, not a restore script, and the manifest says so in a restore_gaps field rather than letting the file imply more coverage than it has.

07 / NEXT STEPS

What to do next, why, and what you should expect to happen

Ordered by what blocks money and what breaks trust. Open any row for the reasoning.

1 Decide what the 50 percent discount code actually is your call▸
Situation
Two codes exist and only one of them is real. Each buyer gets a unique generated code stored on their preorder row, for example 4K25RJ. The email sends PREORDER50, a single shared coupon, and that is the one that actually redeems at Stripe. The per-buyer code is not a Stripe object and redeems nothing.
Why it matters
A shared 50 percent off code sitting in every buyer's inbox is one screenshot away from being public. It is also the opposite of what you specified in requirement one.
Recommendation
Keep the per-buyer code as proof of preorder now, and mint real single-use Stripe promotion codes in bulk at launch, generated from the preorders table. A promotion code should be restricted to the product it is for, and the launch product does not exist in Stripe yet, so there is nothing correct to restrict it to today.
Expected outcome
Every buyer holds a code only they can redeem, once, against the book and nothing else. A leaked code costs you one discount instead of all of them. Nothing needs to change in the email template today beyond removing the shared code.
Blocked on
You. This is a pricing and trust decision, not a technical one.
2 Go live on Stripe, with a separate live-mode webhook secret blocks revenue▸
Situation
All 13 checkout sessions are cs_test_. The store collects nothing. Going live needs live keys, live-mode prices, and a separate live-mode webhook endpoint with its own whsec_.
Why the webhook is the dangerous part
Test and live webhooks never share a signing secret. Miss that step and the failure is silent and total: payments arrive, signature verification fails on every one, and every fulfillment dies while Stripe shows successful charges. It is the most common way a go-live breaks.
Recommendation
Do it as one deliberate pass, then run one real purchase with a real card and confirm all seven downstream effects before announcing anything: cs_live_ session, ledger row, preorder row, download email, admin email, working zip, and a 200 on the Stripe webhook. Refund it afterwards.
Expected outcome
The store takes real money and every existing test-mode download link keeps working, because the success page already falls back to fulfilled_sessions rather than depending on a live key retrieving a test session.
Note
Leave STRIPE_PRICE_ID_AUTHORS unset. The Author's Edition returning 503 is deliberate and correct. It is not for sale and no UI exposes it.
3 Collect the email before checkout, not after the charge before go-live▸
Situation
stripe-checkout passes customer_email: undefined, so Stripe collects the address during checkout and the app cannot know who the buyer is until after they have been charged. The unique(email, edition_type) constraint then blocks the second row.
Why it matters
In test mode this is invisible. With live keys, a repeat buyer is charged and deduplicated afterwards, with no refund path. That is a chargeback and an angry email, and it is exactly the case requirement four was meant to prevent.
Recommendation
Collect the email on the page before creating the session, check it against preorders, and if they already own a copy, resend their download instead of opening a checkout. This is a UI change, which is why it is ranked below the two above.
Expected outcome
A returning customer gets their bundle back instantly and is never charged twice. One copy per address becomes true at the moment it is claimed rather than after the money has moved.
4 Put one backup copy somewhere that is not this laptop finishes req 6▸
Situation
The nightly job is running and verified, but Supabase and every backup of it are now reachable from one machine in one room.
Why it matters
Two copies in one apartment is redundancy against a dropped table, not against a lost laptop, a theft, or a failed disk. Requirement six said "more than one place" and this is the half that is still literal.
Recommendation
Cheapest correct move: point BACKUP_DIR at an iCloud or Dropbox folder, or add one line to the wrapper that rsyncs the newest dated directory to an external drive or an R2 bucket. The files are 40 KB a night without the bundle, so this costs nothing.
Expected outcome
Losing the machine stops being an event that loses the business's customer records.
5 Add one Cloudflare WAF rate limiting rule 10 minutes▸
Situation
rateLimit.js keeps counters in module scope. On Cloudflare Pages those live in an isolate that recycles constantly, so an attacker spreading requests resets the limiter without trying. Tonight's origin fix closed the cheaper half of this, because headerless scripted POSTs are now refused outright.
Recommendation
A WAF rate limiting rule, which never reaches your isolate and needs no code. Free plan allows one: match URI Path starts with /api/ AND does not start with /api/webhooks/, at 20 requests per minute per IP, block for 10 minutes.
Why the webhook exclusion is not optional
Resend and Stripe deliver in bursts from a small pool of IPs. Include them and you will rate limit your own payment confirmations, which turns a security control into the outage it was meant to prevent.
Expected outcome
A flood costs an attacker a block instead of costing you your Resend quota and sender reputation, which is the expensive thing to repair.
6 Fix the DMARC record deliverability▸
Situation
Cloudflare's security overview flags a DMARC record error on the domain.
Why it matters
It affects deliverability of exactly the transactional emails the new ledger tracks. The whole fulfillment guarantee ends in an email arriving. A perfect database row and a bounced message is still a customer who did not get their book.
Expected outcome
Download emails land in inboxes rather than spam, and the email_deliveries table starts showing delivered instead of bounced as volume grows. Worth doing before any launch push, not after.
7 Two small ones: the download URL, and the Empirica harness when convenient▸
Download URL
A customer reported a broken download and it has never been diagnosed because the failing URL was never supplied. Count the characters after session_id=. It must be 66. Shorter or punctuated means something rewrote the link in transit, an email client or a link tracker, and the bug is not in the site at all.
Empirica harness
qdrant_client is not installed, so auto-embed and eidetic ingestion fail on every artifact and project-search is blind to anything logged. Artifact routing also auto-detects the wrong project from this repo, so --project-id survivingthesingularity has to be passed explicitly.
Expected outcome
Neither blocks revenue. Both are the kind of small broken thing that quietly wastes an hour later.
08 / BOTTOM LINE

Where this leaves you

Trust the plumbing

The pipeline that takes a payment and turns it into a delivered bundle is now durable, logged end to end, and self-repairing when a step dies. Abandoned checkouts are recorded. Emails are recorded once each. The endpoints in front of it refuse anything that cannot prove it came from your own site. The database has a checked, automated second copy.

Every one of those claims was proven against production tonight, not read off the code.

Do not trust the revenue

None of it has processed a real payment. Test mode is a rehearsal, and the one part of a go-live that fails silently, the webhook signing secret, is the part that has never been exercised in live mode.

The correct next move is not more hardening. It is one real transaction with a real card, watched all the way through to the zip file downloading.
