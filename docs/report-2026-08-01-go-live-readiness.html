02 · The finding that matters

A missing table turns a safety feature into silent revenue loss

The webhook writes a financial ledger row before it does anything else, and that write fails closed on purpose. The reasoning in the source is sound: losing the financial record destroys chargeback defence, and Stripe retries for about three days at no cost, so returning 500 keeps the order recoverable.

That design is correct. It is also what converts an unrun migration into total revenue loss. checkout_transactions is created by sql/013_checkout_durability.sql. The go-live doc's pending-migration list reads 002, 008, 009, 010 and is dated 2026-07-28, which predates both 013 and 014. That list understates the risk.

The distinction that makes this dangerous: configured:false is returned only when Supabase is not wired up at all, which is normal in local dev and correctly does not 500. A missing table with Supabase wired returns {ok:false, configured:true}, which is the exact combination that triggers the 500. Local dev will never show you this.

04 · The moving part

Two paths race to fulfill every order

The design's cleverest property is that fulfillment has two independent entry points which cannot collide. Drag to orbit, scroll to zoom.

Drag to rotate · scroll to zoom · the red node is the unverified gate

Blue: the fast path

The customer's browser lands on the success page after paying. It fulfills immediately, so most customers get their email within seconds.

Amber: the truth path

Stripe fires server to server the moment payment confirms. This one runs even if the customer closed the tab, lost signal, or crashed.

Red: the unverified gate

Only the webhook passes through the ledger. If checkout_transactions is absent, this node returns 500 and the amber path never reaches fulfillment.

Whichever path arrives first calls claimSession, which inserts a row against a unique constraint on session_id. The loser becomes a no-op, so the customer is never double-emailed. When prior state cannot be determined, the code deliberately errs toward delivering twice, on the reasoning that a duplicate email is an apology and a lost order is a refund and a lost customer.

05 · The test suite, decomposed

398 failures, and what they actually were

A 39% failure rate reads like a broken product. It is not. Grouping by error message rather than by count splits the number cleanly, and the residue is smaller and more specific.

The 304 are one missing binary

All three top-failing projects are WebKit: webkit, mobile-safari, tablet. Every one threw the same launch error. npx playwright install webkit clears all 304.

The 18 checkout failures are the missing .env

All nine assertions fail identically across three engines, including a basic DOM presence check. With no Supabase credentials, the duplicate-order check cannot run, and the endpoint refuses with 503 rather than risk a double charge. Correct behaviour, failing tests.

What genuinely passed and matters: the four money-path specs, 773 lines of real assertions over duplicate handling, event freshness, admin tokens and reconcile format. They import the actual decision functions and never touch a server, which is why they pass with no credentials. That verifies the policy layer. It does not verify the HTTP path around it.
