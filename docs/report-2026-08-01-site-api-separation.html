Session report · 1 August 2026 · sts-v0.7.3

The site API stopped repeating itself, and grew a gate that says so.

Five consumers each re-derived what the book is from the same two files. The download filename was spelled in four places, and on 2026-08-01 that cost a production 404. Three waves collapsed the duplication to one reader per runtime, deleted the third implementation entirely, and added a check that fails the build when the two survivors disagree. One filter turned out to have been dead for some time.

What changed, part one

One string, spelled in four places

The mechanism first. Every surface that offers the book built its own filename from book.json’s version field, using its own copy of the same template literal. Nothing held those copies together, so they could disagree, and they did: book.json said 0.7.4, static/downloads/ held 0.7.2, and the link generated correctly, pointed at a file that had never shipped, and 404’d for every friend handed the password.

The publish script is the new box. It copies book-build/ into static/downloads/ with names derived from the manifest, and it is idempotent by content hash, so re-running it after an unchanged rebuild is a no-op. It is not in prebuild on purpose, and the guard now fails with fix: npm run book:publish instead of a cp line to retype.

Why the stress suite’s green is not vacuous

scan.finds_all asserts it finds 3 cross-reference edges, and the real manuscript contains zero. That assertion can only pass if the resolver is genuinely reading the throwaway copy it was handed. The test proves its own wiring, which is what made it safe to delete the global it used to rebind.

Why the parity check is half-exercised

It has two arms. The section arm compares all 30 titles and is fully live. The pointer arm compares every sts: reference in the book, and there are currently none, so it is vacuous on real content. I injected a real reference into a chapter to exercise it, confirmed both failure modes, then reverted. Treat the pointer arm as tested but not yet load-bearing.

The node that was deleted

The edge that is new

check-resolver-parity.mjs runs both rule sets over the same manifest and fails the build if one label disagrees. It costs 0.7s and sits in prebuild.

What changed, part two

Two implementations, made honest

A cross-reference is written as a pointer, [](sts:chapter1), and rendered as “Chapter 1” from the manifest, so renumbering a chapter rewrites the sentences pointing at it rather than leaving prose that is quietly wrong. Something must turn the pointer into words, and two runtimes need to: Python for the book builds, JavaScript for the site, which cannot call Python at build time.

Three implementations existed. The bash one is gone. The remaining two are not held together by discipline, they are held together by a gate.

The gate is directional. Both resolve but disagree, or Python resolves where the site drops the marker: build fails. The site resolves where Python refuses: a note, because Python checks block ids against the manuscript index and is meant to be stricter, and its own build already stops first.

The filter that had already died

build-epub.sh excluded the print index with grep -v '^18-index.md$'. There is no 18-index.md and no index section in book.json: the pattern matched nothing while still reading like a live filter. Harmless today, a trap the moment an index returns. The replacement excludes by section id, which survives renumbering; filenames carry an ordinal prefix and do not.

The global that hid a dependency

ref_edges read the module-level BOOK_DIR, so the stress test declared global BOOK_DIR and rebound it to a temp tree: a test faking its environment by mutating a global owned by the module under test, leaving the real manuscript one early return away from being the thing under test. It now takes the directory as an argument. The global is gone.

Bottom line

What to rely on, and what not to yet

Safe to rely on

  • The download filename has one definition. Four surfaces import it. The class of bug that 404’d in production cannot recur from a copy drifting, because there are no copies.
  • A forgotten publish fails the build. Watched: exit 1 with the file named, exit 0 after npm run book:publish.
  • The EPUB build is behavior-preserving. Real pandoc and weasyprint run, producing a section set identical to the shipped v0.7.4.
  • The section-label rule agrees across runtimes. All 30 verified, and the check was watched failing three different ways.
  • The CLI surface is unchanged. All 23 subcommands parse and the ones touching the manifest were run, not just --helped.

Do not rely on yet

  • The pointer arm of the parity check. Zero cross-references exist in the book, so it compares an empty set. Tested with an injected fixture, not by production content.
  • The release path end to end. Proven against a synthetic deletion, never against a real version bump. RETIRED_VERSIONS is still hand-maintained.
  • sts.py being “split.” Two concerns of roughly eight are out. It is 5,239 lines and still the most-touched file in the repo.
  • Commit 1910c3b being only my work. It carries another session’s guard and their unstaged rewrite of the friends-only page. Disclosed in the message; review before pushing.
  • Anything about production. Nothing here was deployed or probed live. Every claim is local: build output, exit codes, and file contents on disk.
